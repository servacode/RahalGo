## 1. الرؤية والنطاق

**RahalGo** منصة توصيل طلبات **متعددة الفئات** (مطاعم، بقالة، صيدليات، هدايا، "اطلب أي شيء") تعمل **حصراً في محافظة الرقة** كمرحلة أولى، مع بنية جاهزة للتوسع لاحقاً إلى باقي المحافظات السورية.

الهدف: أن تكون المنصة **الأولى في السوق السورية بلا منافس** من حيث الاكتمال والاحترافية — لا نسخة تجريبية ولا حلولاً مؤقتة؛ كل مرحلة تُسلَّم منتجاً كاملاً.

## 2. خلاصة بحث السوق

تمت مراجعة أكثر من 45 تطبيقاً قبل وضع هذه الخطة:

- **عالمياً**: DoorDash، Uber Eats، Deliveroo، Just Eat، Delivery Hero، Glovo، Wolt، Bolt Food، foodpanda، Grab، Gojek، Meituan، Ele.me، Zomato، Swiggy، iFood، Rappi، PedidosYa.
- **عربياً وإقليمياً**: طلبات، هنقرستيشن، جاهز، مرسول، كريم فود، نون فود، نعناع، تويو، InstaShop، Keeta، سنونو، رفيق، ياسر، Toters، بلي، Lezzoo، عالسريع، TipTop، Snapp Food.
- **تركيا** (النموذج الأقرب لواقعنا): Yemeksepeti، Getir/GetirYemek، Trendyol Yemek، Tıkla Gelsin، Migros Yemek/Hemen/Sanal Market، Fuudy، Banabi، İstegelsin، CarrefourSA.
- **سوريا**: BeeOrder، شام إيتس، سريع، اطلبني، بوسطجي، Movo، NexMove، يلا دليفري، ONA Syria، Speed Delivery.
- **الرقة**: ديلفري الرقة (التطبيق الوحيد المتخصص) + خدمات غير رسمية عبر فيسبوك/واتساب.

**الفجوة السوقية**: لا يوجد في الرقة (ولا في سوريا عموماً) منصة متعددة الفئات بأربع واجهات كاملة (زبون/سائق/متجر/عمليات) مع محفظة داخلية وتشغيل مُحكم للنقد — هذه هي الفرصة.

## 3. الأدوار والحسابات (مثبّت)

كل دور له حساب خاص وصلاحيات دقيقة ولوحة/تطبيق مخصص:

| الدور | الوصف | آلية العمل المالية |
|---|---|---|
| **الزبون** | يطلب من كل الفئات | نقد عند الاستلام + محفظة داخلية |
| **السائق** | مستقل **بنظام العمولة** | عمولة من كل توصيلة، سقف نقدي، تسوية صندوق يومية، لوحة أرباح شفافة |
| **المتجر** (مطعم/بقالية/صيدلية/…) | حساب مستقل لكل محل | عمولة على الطلبات + فاتورة دورية واضحة |
| **مندوب المبيعات** | **مروّج ميداني تابع للمنصة** (لا علاقة عمل له بالمتجر): له **كود دعوة فريد** (RH-XXXXX)، يعرض المنصة على المحلات فتُسجَّل بكوده وتُنسب له | **عمولة من المنصة** (نسبة من عمولتها على طلبات متاجره — قابلة للتهيئة من الإعدادات)، لوحة متابعة | 
| **موظف العمليات** | غرفة القيادة اليومية | إسناد يدوي، تدخل، إدخال طلبات هاتفية |
| **المدير المالي** | التسويات والفواتير والتقارير | صلاحيات مالية فقط |
| **الأدمن** | تحكم كامل بالمنصة | إدارة كل شيء |

## 4. المعمارية العامة

**مبدأ API-First**: كل منطق العمل في الخادم؛ الويب والأندرويد واجهات تستهلك نفس الـAPI. بناء الويب أولاً يختبر الـAPI ميدانياً، فيصبح التطبيق في نهاية المشروع عمل واجهات بنسبة ~80%.

```
┌──────────────────────────────────────────────────────────┐
│              الخادم المركزي — Go                          │
│  REST API + WebSocket + بوت واتساب + مهام خلفية           │
│  PostgreSQL/PostGIS + Redis                              │
└──────┬───────────┬──────────────┬───────────┬────────────┘
   لوحة الأدمن   بوابة المتاجر   موقع الزبون   تطبيقا أندرويد
   والعمليات     (ويب)          (ويب)        (زبون + سائق)
   والمالية                                   + لوحة المندوبين
```

## 5. التقنيات المعتمدة (مثبّت)

| الطبقة | التقنية | المبرر |
|---|---|---|
| الخادم | **Go** (أحدث إصدار مستقر) | أداء وتزامن استثنائيان للاتصالات الحية، استهلاك موارد ضئيل، ملف تنفيذي واحد سهل النشر |
| API | REST (JSON) + WebSocket للحالة الحية | معيار مفهوم لكل الواجهات |
| قاعدة البيانات | **PostgreSQL + PostGIS** | موثوقية مطلقة + استعلامات جغرافية (المناطق، أقرب سائق، المسافات) |
| الحالة اللحظية | **Redis** | مواقع السائقين، الجلسات، الطوابير |
| رسائل التحقق | **بوت واتساب** عبر مكتبة **whatsmeow** (Go) | قرار مثبّت: لا SMS؛ OTP وإشعارات عبر واتساب |
| الويب | **Next.js (React + TypeScript) + Tailwind** لكل الواجهات الويب (موقع الزبون + جميع اللوحات) | إطار موحّد واحد: مكونات مشتركة وقاعدة كود واحدة، مع SEO لموقع الزبون |
| الأندرويد | **Kotlin + Jetpack Compose** — أصلي 100% | قرار مثبّت: لا تطبيقات مغلّفة |
| الخرائط | **OpenStreetMap** ببلاطات ذاتية الاستضافة + **OSRM** للمسافات والمسارات | بلا رسوم أو قيود إقليمية؛ قرار مثبّت |
| الاستضافة | **Hetzner** + Docker Compose + Caddy (TLS تلقائي) | قرار مثبّت |
| CI/CD | GitHub Actions | بناء واختبار ونشر آلي |

## 6. الأنظمة الجوهرية

### 6.1 دورة حياة الطلب (آلة حالات صارمة)

```
Pending → Accepted → Preparing → (بالتوازي: Dispatching → Assigned)
→ AtPickup → PickedUp → OnTheWay → AtDropoff → Delivered
مسارات استثنائية: Rejected / Cancelled / Failed / Refunded
```

- كل انتقال له: مؤقّت مراقبة + إشعار للأطراف + قاعدة تصعيد آلي للعمليات.
- عدم قبول المتجر خلال المهلة ⇒ تنبيه أحمر في غرفة العمليات.
- سجل تدقيق (Audit Log) كامل لكل تغيير حالة: مَن، متى، لماذا.

### 6.2 الإسناد (Dispatch)
- تلقائي: أقرب سائق متاح (PostGIS) مع مراعاة حِمله وسقفه النقدي.
- يدوي: من غرفة العمليات في أي لحظة.
- لاحقاً: تجميع طلبات (Batching) بمسار واحد.

### 6.3 النظام المالي النقدي
- **السقف النقدي للسائق**: تجاوزه يوقف استلام طلبات نقدية حتى تسليم الصندوق.
- تسوية يومية: نقد الشركة/المتاجر مقابل أجور السائق — بتقرير مفصل.
- **المحفظة الداخلية** للزبائن: شحن عبر نقاط بيع معتمدة، تعويضات فورية للشكاوى.
- عمولات قابلة للتهيئة لكل متجر ولكل مندوب مبيعات.

### 6.4 العنونة (مصمّمة لواقع الرقة)
- دبوس على الخريطة + حقل وصف إلزامي ("جانب جامع…") + عناوين محفوظة (البيت/العمل).
- لا اعتماد على عنونة رسمية غير موجودة.

### 6.5 بوت الواتساب
- OTP للتسجيل والدخول، إشعارات حالة الطلب الاحتياطية، تواصل خدمة العملاء.
- **إدارة المخاطر**: أرقام مخصصة، حدود إرسال متدرجة، قوالب ثابتة، خطة ترقية مستقبلية إلى WhatsApp Business API الرسمي عند توفر قناة — مع إبقاء بنية الإرسال مجرّدة (Provider Interface) بحيث يكون التبديل تهيئةً لا إعادة برمجة.

### 6.6 محرك العروض
أكواد خصم (نسبة/مبلغ/توصيل مجاني، حد أدنى، أول طلب، مرة لكل مستخدم، انتهاء صلاحية) + بانرات ديناميكية تُدار من اللوحة دون تحديث تطبيق.

### 6.7 الجودة والدعم
- تقييم مزدوج بأسباب جاهزة.
- نظام تذاكر مع تعويض بالمحفظة وصلاحيات تصعيد.
- مقاييس تشغيل: زمن التوصيل، نسب الإلغاء، أداء السائقين والمتاجر.

### 6.8 صمود الشبكة (خصوصية سورية)
- التطبيقات تخزّن الحالة محلياً وتزامن عند عودة الاتصال.
- واتساب كقناة إشعار احتياطية عند فشل Push.
- عمليات حرجة (تسليم/تحصيل) تعمل بلا اتصال وتُرفع لاحقاً.

## 7. مراحل التنفيذ (كل مرحلة منتج كامل)

### المرحلة 0 — الأساسات
هيكل Monorepo، قواعد الكود، Docker Compose للتطوير، قاعدة البيانات والهجرات، هيكل الـAPI، CI.

```
RahalGo/
├── backend/     # Go: API + WebSocket + بوت واتساب + مهام خلفية
├── web/         # admin/ merchant/ customer/ sales/ (Next.js + TS)
├── android/     # customer/ driver/ (Kotlin+Compose) — المرحلة الأخيرة
└── docs/        # الوثائق والقرارات
```

### المرحلة 1 — الهوية والحسابات + لوحة الأدمن (نقطة البدء المتفق عليها)
- تسجيل/دخول برقم الهاتف + OTP واتساب، كلمات مرور، JWT + Refresh، أدوار وصلاحيات كاملة (RBAC) للأدوار السبعة.
- لوحة أدمن كاملة: المستخدمون، المتاجر وقوائمها (مع المُعدِّلات Modifiers)، مناطق التغطية على خريطة تفاعلية، رسوم التوصيل لكل منطقة، أكواد الخصم، البانرات، الإشعارات، حسابات المندوبين وربط المتاجر بهم.

### المرحلة 2 — محرك الطلبات + غرفة العمليات
دورة الحياة كاملة بالمؤقتات والتصعيد، الإسناد التلقائي واليدوي، النظام المالي النقدي والمحفظة، خريطة العمليات الحية، إدخال الطلبات هاتفياً، التقييمات، التذاكر، التقارير.

### المرحلة 3 — بوابة المتاجر + موقع الزبون + لوحة المندوبين (ويب)
- بوابة المتجر: استقبال برنين مستمر، إدارة القائمة والتوفر (إيقاف "نفد")، أوقات الدوام، التقارير والفواتير.
- موقع الزبون الكامل: تصفح، سلة، طلب، تتبع حي — اختبار ميداني شامل للـAPI.
- لوحة المندوب: تسجيل متاجر جديدة، متابعة العمولات والأهداف.

### المرحلة 4 — تطبيقا الأندرويد الأصليان
- **الزبون**: كامل الميزات + Push + تتبع حي + محفظة.
- **السائق**: ورديات، عروض طلبات بمهلة قبول، ملاحة، إثباتات استلام/تسليم، GPS خلفي، الصندوق والأرباح، عمل دون اتصال.

### مؤجَّل عمداً لما بعد الإطلاق
تجميع الطلبات، التسعير الديناميكي (Surge)، اشتراك التوصيل المجاني، الإعلانات المدفوعة للمتاجر، iOS، التوسع الجغرافي.

## 8. البنية التحتية

- خادم Hetzner (يُحدد الحجم عند النشر؛ البداية بخادم واحد قوي + ترقية عمودية سهلة).
- Docker Compose لكل الخدمات، Caddy للـTLS التلقائي.
- نسخ احتياطي يومي مشفّر لقاعدة البيانات خارج الخادم + اختبار استرجاع دوري.
- مراقبة: Uptime + سجلات مركزية + تنبيهات.
- بيئتان: Staging وProduction.

## 9. الأمان

- تجزئة كلمات المرور (bcrypt/argon2)، صلاحيات RBAC صارمة، تحديد معدلات الطلبات (Rate Limiting).
- تأكيد الهاتف إلزامي + حد أقصى لقيمة أول طلب نقدي (مكافحة احتيال).
- حظر جهاز/رقم، سجل تدقيق كامل، HTTPS حصراً، أسرار خارج الكود.

## 10. المخاطر الرئيسية والتخفيف

| الخطر | التخفيف |
|---|---|
| حظر رقم بوت الواتساب | أرقام احتياطية + حدود إرسال + بنية مزوّد قابلة للتبديل |
| انقطاع الإنترنت/الكهرباء بالرقة | تصميم Offline-first + قنوات احتياطية + عمليات هاتفية |

| منافس محلي قائم (ديلفري الرقة) | التفوق بتعدد الفئات والمحفظة والتشغيل الاحترافي |
